Translation Layer / Recommended Design

把 Translate Layer 从“大 Prompt”升级成 Translation Harness

目标不是堆更多 Agent，而是让 DeepSeek 在一个受控但不僵化的环境里：知道当前需要知道什么、能主动获取什么、知道什么结果不能接受，并在失败后有明确的修复路径。

Context
知道什么

决定模型当前看到哪些信息。

Tools
还能查什么

允许模型按需获取额外证据。

Guardrails
不能违反什么

定义输入、输出、知识、状态与质量边界。

Loop 把 Context、Tools、Guardrails 组合起来：翻译 → 验证 → 诊断 → 修复 → 再验证 → 通过后落盘。
关键纠正：Guardrail ≠ Hook。Hook 是让某些约束在生命周期节点自动执行的机制；Guardrail 本身是对 Agent 行动、状态和输出施加的边界。

1. 推荐的 Translate Harness

第一版不要做成复杂的 Multi-Agent Team。Translation Agent 仍然可以由一个 DeepSeek 负责推理，外部能力由机械脚本、视觉模型和工具提供。

职责边界

组件核心问题不应该负责什么
Context Builder当前这一页需要知道什么？不替模型完成翻译推理
Tools模型还可以主动查什么？不把所有知识预先塞进 Prompt
Translator基于当前证据做翻译判断不自行宣布“通过”
Validators机械上是否违反硬约束？不判断所有主观语言质量
Evaluator译文质量到底有多好？不直接修改结果
Loop失败后如何诊断、修复、重验？不无限重试
State成功后留下哪些可复用信息？不把一次推测直接升级成 Canon

2. 先解决“翻译到底好不好”：Eval

Translation Harness 的第一块地基不是 Hook，而是可量化的质量标准。不要让 Translator 自己说“我翻得不错”。把“好”拆成四个维度，并为每个维度定义评分与通过条件。

Accuracy

语义准确

人物关系、动作、语气、否定、程度、隐含信息不能被改变。

参考集 + 语义评估

Fluency

中文自然

像中文漫画对白，而不是逐字日译中。

独立 LLM Judge / 人工抽检

Consistency

全作一致

人名、地名、作品术语、角色称呼、固定译法保持一致。

机械 Validator 最强

Readability

漫画可读

句长、断行、气泡空间、字号与画面关系合理。

Programmatic QA + Vision QA

Golden Set
  ├── source_text

PASS / FAIL
不要把 BLEU 当核心指标。漫画翻译允许大量等价表达；字符串越像 Reference 不代表越自然。Reference-based 指标可以辅助，核心应是语义判断、Consistency 机械检查以及少量人工校准。

第一版建议

先建立一个小而可靠的 Golden Set，而不是追求巨大数据集。优先覆盖：角色口癖、暧昧句、否定句、SFX、Touhou 固有名词、容易 OCR 混淆的词、跨页连续对白。

3. Guardrails：不是“一堆 Hook”，而是约束体系

Guardrail = 限制 Agent 输入、行动、状态修改和输出的边界。 Hook 只是其中一种执行方式。

Guardrail 类型漫画翻译例子主要实现
Inputpage_id、text_id、坐标、原文候选必须存在Schema / Validator
Output每个 text_id 必须有译文；不得凭空产生新的 text objectJSON Schema / Validator
Knowledge已确认的 豊姫 → 丰姬 不得静默改写Glossary / State Policy
ToolOCR 冲突时可查 Vision；不是每句话都重复调用Tool Contract / Policy
State Mutation“灵梦喜欢魔理沙”只能先作为 inferred/candidate，不能直接成为 canonical factProposal → Validation → Commit
QualityConsistency 违规或语义分低于阈值不得通过Eval + Acceptance Policy

Soft / Hard / Lifecycle 三层

Soft

告诉模型应该怎么做

Prompt / Context：保持角色语气、优先利用上下文、不要过度解释。

Hard

违反就 FAIL

Schema、Glossary Validator、Coverage Check、State Mutation Rules。

Lifecycle

不能跳过检查

Hook / Script：进入 Translate 前检查输入，完成后强制跑 Validator 与 Eval。

一句话：Prompt 是“应该”；Guardrail 是“不能”；Hook 是“在什么时候自动执行这个约束”。

Translate Layer 真正需要的 Hook 很少

Lifecycle检查
pre-translate输入 Schema、page/text IDs、OCR candidates、State 文件完整性
post-translate输出 Schema、覆盖率、Glossary violations、State update schema
on-failure触发 repair/retry，并记录失败原因

其他规则直接写成 Validator / Test，不需要为了“看起来像 Harness”而全部 Hook 化。

4. Loop：翻译不是一次调用，而是受约束的验证—修复循环

Build Context
      ↓
Translate
      ↓
Deterministic Validators
      ↓
Independent Evaluator
      ↓
   PASS?
   /   \
 NO     YES
 │       │
Diagnose Persist
 │       │
Repair  Update State
 │
Re-translate / Re-verify
 │
 └──────────────→ PASS

失败必须有原因，而不是“再来一次”

Failure诊断Repair
Glossary violation术语不一致锁定 canonical term 后重译
Missing text_id输出覆盖不完整补齐遗漏项
Semantic score low意义发生偏移重新读取 source/context/vision 后重译
Fluency low机器翻译腔保留语义约束，重写中文表达
Character voice low角色口吻不符检索该角色 recent examples 后重译
设置 retry budget。例如同一 text/page 最多自动修复 2~3 次；仍失败则标记为 needs_review，不要无限循环。
Eval
“有多好？”

输出 Accuracy / Fluency / Readability 等分数或诊断。

Guardrail
“能不能通过？”

把评估结果转换成明确的 acceptance policy：低于阈值、违反硬规则 → FAIL。

5. Context 与 State：让 Agent 动态探索，而不是塞一大坨 Prompt

Context 的目的不是把整本漫画全部注入 DeepSeek，而是提供一个当前决策所需的最小上下文，并允许 Agent 通过 Tools 主动扩展观察范围。

                      │
                      ↓
               Context Builder
                      │
       ┌──────────────┼──────────────┐
       ↓              ↓              ↓

       │              │              │
       └──────────────┼──────────────┘
                      ↓
                  DeepSeek
                      │
             “我还缺什么信息？”
                      │
                ┌─────┴─────┐
                ↓           ↓
          lookup_term     vision
                │           │
                └─────┬─────┘
                      ↓
                Better Context
                      ↓

State 不应该只有“事实”，而应该带置信度

fact
├── canonical       已确认事实
├── observed        直接观察到
├── inferred        模型推断
└── candidate       待确认

每个 State Update：
subject
predicate
object
status
evidence
source_page
confidence

这样可以允许关系、称呼、角色身份、作品内设定随剧情发展而变化，而不会因为一次推断污染整个 Work State。

最小运行接口

result = translation_loop.run(page)

# 内部：
context = context_builder.build(page, state)
draft = translator.translate(context, tools)
validation = validators.run(draft, state)
evaluation = evaluator.run(page, draft, context)

if not acceptance_policy.pass_(validation, evaluation):
    draft = repair(draft, validation, evaluation)
    # bounded retry

if passed:
    state.commit(draft.state_updates)
    return final_translation
else:
    return needs_review

第一版不要做的事情

  • 不要建立 Planner / Translator / Reviewer / Researcher 四五个 Agent Team。
  • 不要把所有 Guardrail 都实现成 Hook。
  • 不要让 DeepSeek 自己修改 canonical knowledge。
  • 不要用 BLEU 一个数字代表漫画翻译质量。
  • 不要让模型自己决定“我已经验收通过”。
  • 不要无限 Repair Loop。

7. 建议实施顺序

① Golden Set
→
② Validators
→
③ Evaluator
→
④ Context Builder
→
⑤ Tools
→
⑥ Repair Loop
→
⑦ State Commit

Phase 1 — 先让“好坏”可测

建立 Golden Set + 四维评分标准 + Acceptance Policy。没有这个，后面的 Harness 只能凭感觉优化。

Phase 2 — 先机械约束，再让模型发挥

Schema、Coverage、Glossary、State Mutation、Output Validation。

Phase 3 — 让模型拥有按需探索能力

Context Builder + lookup tools + Vision tool。默认给最小上下文，模型发现缺信息再查。

Phase 4 — 把失败变成 Repair Loop

Validator/Evaluator 给出结构化 failure reason，DeepSeek 根据原因修复，限制 retry budget。

Phase 5 — 成功后才更新 State

把 confirmed / observed / inferred / candidate 分层；只有符合规则的更新才能落盘。

最终目标：不是把 DeepSeek 管得越来越死，而是把“必须正确的部分”机械化，把“需要理解和判断的部分”留给模型。
Mechanical where possible, agentic where necessary.
Translation Harness v1 — Design Summary
适用于当前 Touhou Doujin Manga Translation 项目。核心结构：Context · Tools · Guardrails · Loop；外围由 Eval、State 和 Lifecycle Hooks 支撑。
