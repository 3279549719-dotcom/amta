1 总览

一句话结论

8 个项目全部不引入依赖——个人 DIY + 最小依赖哲学(第三方库仅 requests/pillow)下,自写 ~100 行编排器 + pipeline_log + LLM logger,借鉴思想、不背行李。

调研方法

3 个并行 subagent:① Prefect/Metaflow ② OpenTelemetry/Dagster ③ LangSmith/LiteLLM/Pydantic。每个项目核实:依赖体积、本地运行是否强制服务、断点机制、tracing 导出、Windows 兼容。

2 8 项目逐项结论

项目Star类别结论原因(关键事实)
Prefect23.7k工作流编排❌ 不引pip 引入 ~60 直接依赖、数百 MB(fastapi/sqlalchemy/uvicorn…);断点是"整体重跑+缓存跳过"的弱化版;无本地 JSON 日志导出;起 server 才留历史
Metaflow10.2k工作流编排❌ 不引功能完美(resume 断点/全本地/仅 2 依赖),但官方不支持原生 Windows(fcntl,要 WSL2)——出局
Dagster10k+工作流编排❌ 不引比 Prefect 更企业级(webserver/DB),3 个线性脚本用它是杀鸡用牛刀
LangSmith8k+LLM 观测❌ 不引数据强制上云(免费版传 LangSmith 云端,自托管是 Enterprise);14 个自带依赖——违反本地/不上云哲学
LiteLLM10k+LLM 网关⏸️ 观望依赖 ~100MB;价值=自动成本表 + fallback 一行切千问;单通道场景不值,3+ 供应商(接千问 vision)时再考虑
OpenTelemetry18k+可观测性借思想span 概念正是我们要的;但 JSON 文件导出仍需自写 exporter——直接手写 20 行装饰器 + json.dump 等价
Pydantic19k+契约校验⏸️ 观望最轻(3-5MB),但单一 JSON 契约 30 行手写够用(canon_schema 已有);工具 schema 膨胀到 5+ 嵌套时再引
Great Expectations9.5k+数据质量❌ 不引Expectation Suite 体系对 10-20 页规模过重,Pydantic 都嫌多

4 最终方案(自造,零新增依赖)

① 工作流编排

00_run_all.py:~100 行。01_detect → 02_ocr → 03_translate → ③ 评审 → 自动修复。文件存在=跳过(断点),失败中止留 failed_step 锚点。

② Task Tracing

pipeline_log.json:每步一条 span(step/page/status/input/output/耗时/关键数字),run_id + git_head 记录,append 不覆盖。

③ Agent 观测

03 --trace:每页 LLM 调用摘要(model/token/工具调用次数/返回),探针代码转正,~60 行。

验收路径(已定)

1 页冒烟(单翼第 1 页全链路)→ 把 1-10 页评测产物"转正"为流水线产物 → 从第 11 页起带 work_state 积累续翻(验证 state 跨页累积 + get_context 前页回溯 + 断点续跑)。
