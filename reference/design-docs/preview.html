Agentic Manga Translation Pipeline

一个面向日漫自动翻译的、以 DeepSeek/LLM 为“大脑”、以漫画 CV/OCR/Inpainting 模型为工具的自动化工作流。 核心目标不是制造一个“Multi-Agent Team”，而是把现成的专业模型编排成一个可验证、可重试的生产线。

核心结论： 这不是 Planner Agent + Coder Agent + Reviewer Agent 的多智能体组织。 更准确地说，是 一个具有视觉能力和工具调用能力的 LLM Agent，调用一组非 LLM 的专业模型完成漫画处理，再通过 QA 闭环决定是否重试。

LLM / Agent

DeepSeek（也可以替换为其他 LLM）负责规划、上下文理解、翻译、决策、异常诊断和最终视觉验收。

1. 为什么这不是传统意义上的 Multi-Agent Team

传统 Multi-Agent Team 更像：

Planner Agent
    ↓
Coder Agent
    ↓
Research Agent
    ↓
Reviewer Agent
    ↓
Executor Agent

每个节点本身都是 LLM Agent，拥有自己的推理、任务分解和工具调用能力。

我们的漫画系统更像：

                 ┌──────────────────┐
                 │ DeepSeek / LLM   │
                 │  大脑 / 总控      │
                 └────────┬─────────┘
                          │
       ┌──────────────────┼──────────────────┐
       ↓                  ↓                  ↓
  Manga Detector       OCR Model        Inpainting Model
       ↓                  ↓                  ↓
  “哪里有字？”       “写的什么？”      “背景怎么恢复？”
       │                  │                  │
       └──────────────────┴──────────────────┘
                          ↓
                    Typesetter / QA

因此，更准确的名称是：

LLM Agent + Specialized Vision Tools + Verification Loop

为什么这样更合理？

  • OCR 不需要“思考”，需要稳定地识别字符。
  • 文字检测不需要“规划”，需要尽可能高 Recall 地找出文字区域。
  • Segmentation 不需要“理解剧情”，需要生成精确 mask。
  • Inpainting 不需要“决定角色关系”，需要根据 mask 恢复背景。
  • 真正需要推理的是：上下文、人物语气、歧义判断、工具选择、失败诊断和是否通过验收。

2. Detection / OCR / Bubble / Segmentation 到底有什么区别？

它们不是同一个东西。最简单的区分方式是：在哪里？是什么？气泡在哪里？哪些像素属于它？

模块回答的问题输出主要用途
Text Detection哪里可能有文字？Bounding Box / Polygon发现文字区域
OCR文字写的是什么？字符串 + confidence提取日文原文
Speech Bubble Detection气泡在哪里？Bubble Box / Polygon建立文字与气泡/说话区域的关系
Text Segmentation具体哪些像素属于文字？Pixel-level Mask精确擦字、给 Inpainting 提供 mask

用一个“ドン！！”理解

原图
  ↓
Text Detection
  → [这里大概有文字]

OCR
  → “ドン！！”

Segmentation
  → [这些具体像素是“ドン！！”]

Inpainting
  → 把这些像素对应的原背景恢复回来
注意：“气泡”本身不是“文字”。气泡检测可以帮助判断对白区域，但框外 SFX、旁白、背景文字等可能完全没有传统气泡。

3. 四个核心痛点怎么解决

痛点 A：框外字容易漏

不要让 LLM 单独承担检测。 使用漫画专用 Text Detection + SFX/Onomatopoeia 检测 + 必要时让 VLM 复核。

目标是提高 Recall，而不是让一个 VLM 凭肉眼保证 100% 找全。

痛点 B：日语 OCR 错误

使用 Manga OCR / Manga-specific OCR，而不是普通文档 OCR。对低 confidence、专有名词和角色名触发二次识别。

例如：豊姫 → 星姬 可以通过 Character DB + OCR alternatives + VLM 复核纠正。

痛点 C：翻译缺乏上下文

不要只维护 Character Table。建立持续更新的 Story Memory，并按 Scene 而不是单页翻译。

Memory 包含人物、关系、语气、术语、当前地点、事件、近期对白等。

痛点 D：框外字与复杂背景难擦

不要让 LLM 自己“修图”。先通过 Text Segmentation 得到 mask，再交给专用 Inpainting。

复杂 SFX 不一定强行删除：必要时可以选择保留原文 + 添加译注，以视觉自然为最终目标。

4. 完整 Workflow：每一步到底做什么

① CV 检测

扫描整页，寻找对白、旁白、SFX、框外字等可能的文字区域，并尽量建立区域之间的关系。

输出： text regions / bubble regions / SFX candidates。

② 专用 OCR

对检测出来的文字区域做日语 OCR。低置信度区域可以二次 OCR，并与 Character / Glossary 数据进行校正。

输出： 原文、位置、confidence、候选结果。

③ Story Memory

把当前漫画当成一个持续存在的“故事状态”，而不是一堆孤立页面。

{
  "characters": {
    "豊姫": {
      "zh": "丰姬",
      "speech_style": "温和、正式"
    }
  },
  "glossary": {
    "神社": "神社"
  },
  "current_scene": {
    "location": "神社",
    "event": "两人正在争论"
  },
  "recent_dialogue": ["...", "..."]
}

④ Scene-level Translation

先识别连续场景，再把同一场景中的多页对白一起交给 LLM。这样可以保持上下文、人物关系、语气和指代一致。

⑤ Segmentation Mask

翻译已经确定后，再生成用于擦字的精确文字 mask。这里关注的是“哪些像素属于原文字”，而不是“这句话是什么意思”。

⑥ 专用 Inpainting

把文字 mask 交给漫画/图像 Inpainting 模型，恢复文字下面的背景、线稿、人物、速度线等。

⑦ Typesetting

根据气泡大小、译文长度、人物语气和字体规则，把中文重新放入原页面。需要处理换行、字号、居中、描边、方向等。

⑧ Programmatic QA

先用程序检查“机器可以确定”的错误：遗漏文本、翻译数量不匹配、文字溢出、残留日文、文件损坏等。

⑨ Vision QA

把最终图片交给 VLM/DeepSeek Vision 检查程序难以量化的问题：擦除痕迹、背景破坏、文字遮挡人物、排版不自然、视觉异常等。

⑩ 自动 Repair Loop

QA 不只是给一个分数，而是产生可执行的修复动作。

5. DeepSeek 在整个系统里到底干什么？

DeepSeek 不是负责每个视觉动作，而是负责控制流程和处理需要推理的问题。

任务DeepSeek 是否适合原因
寻找所有文字像素否专业 CV 模型更稳定
日语字符识别不作为主 OCR专用 OCR 更适合
判断“豊姫”还是“星姫”适合需要结合视觉、角色表和上下文
场景理解非常适合LLM 的强项
人物语气与关系非常适合需要长上下文推理
决定复杂 SFX 如何处理适合属于策略判断
判断是否需要重试非常适合属于 Agent 控制逻辑
最终视觉验收适合VLM 可以理解整体视觉效果
一句话：专业模型负责“做”，DeepSeek 负责“决定什么时候做、为什么做、做完是否合格、失败以后做什么”。

6. “AI 自己验收”为什么必须分两层

Programmatic QA

机器硬规则，避免让 LLM 检查它本来就能精确判断的问题。

  • 检测区域是否都有 OCR
  • 原文/译文数量是否一致
  • 是否还有日文残留
  • 译文是否溢出目标区域
  • 图片尺寸、文件格式是否正确

Vision QA

交给 VLM 判断难以写成硬规则的视觉问题。

  • 人物脸/身体是否被破坏
  • Inpainting 是否留下明显痕迹
  • 背景线稿是否异常
  • 排版是否自然
  • 人物语气是否与前文一致
关键原则：不要让 DeepSeek 只回答“看起来没问题”。QA 必须产生结构化结果，例如 PASS / FAIL + issue + page + region + suggested_action，这样 Harness 才能真正自动修复。

7. MVP 应该怎么做

不要一开始就做“一整章无人值守”。先证明最关键的技术链条。

10–20

4
核心技术风险
1
LLM Agent

Benchmark A：检测

重点统计：框内对白、框外对白、SFX、背景文字的 Recall。先回答“到底会漏多少”。

Benchmark B：OCR

重点测试：人名、专有名词、竖排文字、艺术字体、手写字和低清页面。记录 CER / Exact Match / confidence。

Benchmark C：Inpainting

挑选简单背景、复杂背景、人物头发、速度线、建筑等困难区域，比较现有 Inpainting 模型的恢复质量。

Benchmark D：上下文翻译

同一个连续 Scene 分别测试“逐页翻译”和“Scene-level + Story Memory”，比较人物语气、术语、指代和整体通顺度。

MVP 成功标准：不是“所有漫画都能自动翻译”，而是证明这条链条可以稳定跑通，并且失败时能够定位到具体模块。

最终定义：
这是一个单 LLM Agent 驱动的漫画翻译流水线，而不是一个由多个 LLM Agent 组成的组织。 其价值在于：把成熟的漫画 CV/OCR/图像模型编排起来，让 LLM 负责上下文、策略和闭环控制。
