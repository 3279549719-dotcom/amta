```text
## 目标

解决一本漫画内相隔多页的翻译决定丢失，以及可翻译日文残留仍以 `ok` 状态出货的问题。解决方案必须是一般化的书内语义记忆与有界生成—验证—修复闭环，不能成为针对示例字符串的补丁。

真实素材：

- 原图：`D:\我的汉化\汉化作品\东方\幻想乡居民们的赚钱大法！\原图`
- 人工修正后的成品参考：`D:\我的汉化\汉化作品\东方\幻想乡居民们的赚钱大法！\新建文件夹`

已观察到的症状：

- `ヤミツキ茸` 或 OCR 邻近变体在前页曾译为 `迷幻菇`，到第 8 页却保留为片假名。
- `クズ` 或 OCR 邻近变体此前曾译为 `人渣`，第 7 页却残留日文。
- 成品参考已经被人工修改，不是原始失败产物。它只能作为结果参考，不能被描述为恢复出的历史失败证据。

生产规则已经确定：

- 模型第一次作出的书内翻译决定是暂定决定，后续出现时作为强默认。
- 新的上下文、重复证据和一致性检查可以提高置信度，也可以使 Agent 自主修订旧决定；不存在人工确认才能生效的门槛。
- 一次有证据的自动修复后仍无法完全确定时，选择当前证据支持的最佳译文继续出图，同时落盘机器可读的低置信度标记。它不能静默伪装成高置信度 `ok`，也不应阻塞整本流水线。
- 人工 PSD 修复是生产末端兜底，不是本闭环中的审批步骤。当前阶段不需要从 PSD 自动回灌翻译记忆。
- 普通调查、编码、测试、重试和验证不请求人工 Approval。只有缺失的产品决定、不可逆操作、发布/推送或任务范围扩大才允许停下来提问。

## 第一阶段：由你完成设计

先调查当前实现和相关测试，不修改生产代码。区分并用证据验证至少两个相邻机制：跨页翻译决定丢失，以及日文残留检测结果没有驱动修复或降级状态。

环境事实由你读取，不向用户提问。只有会改变产品行为的真实决策才向用户提问，并且每次只问一个问题，附上你的推荐答案。若既有规则已经给出答案，不重复提问。

调查完成后，你自己提出 2—3 个有边界的设计方案，比较复杂度、可追溯性、误绑定风险和运行成本，推荐其中一个。遵循 Bitter Lesson：模型负责语义判断，确定性代码负责证据获取、状态、契约、有界重试、落盘和故障显化。

将用户认可的设计写入：

`docs/superpowers/specs/2026-09-30-book-translation-memory-design.md`

再自行写出可执行计划：

`docs/superpowers/plans/2026-09-30-book-translation-memory.md`

Spec 至少说明组件职责、数据流、记忆的生命周期、OCR 邻近变体如何留下证据、低置信度结果如何表现、失败处理、缓存/重跑语义和测试策略。由你决定具体文件、数据结构与算法；不要让本任务指令替你完成设计。

写完后自查占位符、矛盾、隐藏假设和无法验证的完成条件。向用户展示设计摘要和文件路径，然后等待用户发出一次明确的“执行”指令。这个设计确认是实现授权，不是对最终翻译逐页验收。

## 第二阶段：无人审批执行

收到用户的“执行”后，为完整实施目标创建一个有明确轮数上限的 Goal。使用同一 Goal 自主推进实现、测试、真实样本验证和修复；不要在普通工具调用或每个步骤之间等待用户继续。

先写能够复现行为的最小回归测试，再修改实现。测试夹具保持小型，不提交漫画扫描、模型权重、API 密钥、运行 workspace 或生成页面。现有 `docs/weekly-recap/`、`logs/` 和其他无关改动属于用户，保持不变。

实现必须满足这些结果，而不是某个预设的数据结构：

1. 第 3 页首次出现的未知书内表达能够产生可追溯的暂定决定，无需静态词典预先收录。
2. 第 8 页在超出当前三页窗口后仍能检索并优先复用该决定。
3. 小型 OCR 差异能够通过通用规范化和模型语义判断关联；原形、别名、证据页/region、置信度和来源可追踪。
4. 可翻译日文残留不能静默以普通 `ok` 出货：进行一次有证据的修复；仍不确定时输出最佳结果并附机器可读低置信度状态。
5. 暂定决定能因新证据自动增强或修订，不依赖人工确认。
6. 生产代码、prompt 和专用规则中不硬编码 `ヤミツキ茸`、`迷幻菇`、`クズ` 或 `人渣`。
7. 缓存命中、断点重跑和再次翻译不会无声丢失、重复污染或错误提升书内记忆。
8. 人工 PSD 兜底不成为运行依赖，本阶段不实现 PSD 反向抽取。

使用受支持入口运行真实样本，不手工拼接旧阶段脚本：管线用 `scripts/run_pipeline.py`，产物用 `scripts/artifact.py`，现状用 `scripts/peek.py`，需要视觉报告时用 `scripts/gen_report.py`。不要覆盖上述原图或人工修正目录；使用新的 work-id 写入被忽略的项目 workspace。

验证必须包含：

- 新增或修改的聚焦回归测试先红后绿；
- 相关 translate/orchestrator/guard 测试；
- `uv run python -m pytest -q`；
- `npm run check`；
- 在真实素材或不提交的运行 workspace 上证明跨页复用、OCR 邻近变体证据和残留修复/低置信度分支；
- 最终使用仓库规定的收尾入口完成全量门禁，并准确报告它实际执行了哪些检查。

测试通过不等于语义证据存在。最终报告必须逐条对应八项结果，给出测试名、命令结果、产物查询或运行记录；无法观察的结果标为未知，不得凭配置或 Agent 自述判定通过。

## 自主停止条件

Goal 只使用 DSH 原生终态：

- `complete`：设计、实现、聚焦测试、全量门禁和真实运行证据全部满足，未留下必须由人判断的翻译验收项；
- `blocked`：同一外部阻塞在允许的连续 Goal 轮次内持续存在，并已穷尽安全的替代路径，报告最小阻塞条件和现有证据。若流水线已经输出最佳结果及低置信度标记、可进入最终 PSD 兜底，但工程实现或验证仍有明确缺口，在最终报告中将它分类为 `fallback-delivered`，Goal 状态仍为 `blocked`，不得报告为 `complete`。

不要 git push、合并主分支、删除原始素材或修改验收标准。是否提交由仓库既有收尾协议决定；发布与合并不属于本任务。
```

## 与 Agent 交互时只需要做什么

1. 发送上面的任务指令。
2. 回答它提出的真正产品问题；环境事实让它自己查。
3. 审阅它生成的设计方向。如果方向符合目标，发送一句：`执行。按已批准的 Spec 创建 Goal，自主完成实现和验证，中途不要等待普通审批。`
4. 等待它进入终态。生产中仍漏出的个别文本以后直接在 PSD 中修复，不把逐页人工确认重新塞回 Agent 闭环。
