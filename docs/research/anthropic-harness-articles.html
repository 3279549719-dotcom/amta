What is a tool?
什么是工具？
In computing, deterministic systems produce the same output every time given identical inputs, while non-deterministic systems—like agents—can generate varied responses even with the same starting conditions.
在计算领域，确定性系统在相同输入下永远产生相同输出；而像 agent 这样的非确定性系统，即使起点相同也可能给出不同回应。
When we traditionally write software, we’re establishing a contract between deterministic systems. For instance, a function call like getWeather(“NYC”) will always fetch the weather in New York City in the exact same manner every time it is called.
传统软件是在确定性系统之间建立契约。比如 getWeather("NYC") 这个函数调用，每次都会以完全相同的方式取回纽约的天气。
Tools are a new kind of software which reflects a contract between deterministic systems and non-deterministic agents. When a user asks "Should I bring an umbrella today?,” an agent might call the weather tool, answer from general knowledge, or even ask a clarifying question about location first. Occasionally, an agent might hallucinate or even fail to grasp how to use a tool.
工具是一种新的软件形态，它体现的是确定性系统与非确定性 agent 之间的契约。当用户问“今天要不要带伞”，agent 可能会调用天气工具、可能凭常识回答、也可能先反问地点。偶尔，agent 会幻觉，甚至会搞不懂该怎么用这个工具。
This means fundamentally rethinking our approach when writing software for agents: instead of writing tools and MCP servers the way we’d write functions and APIs for other developers or systems, we need to design them for agents.
这意味着为 agent 写软件时，必须从根本上重新思考做法：不能像给其他开发者或系统写函数和 API 那样去写工具和 MCP server，而要**为 agent 而设计**。
我的批注这段话是理解整篇文章的钥匙：工具是『确定性系统与非确定性 agent 之间的契约』。你用写函数的方式写 find_code.py，正是原文点名的那种错。
Our goal is to increase the surface area over which agents can be effective in solving a wide range of tasks by using tools to pursue a variety of successful strategies. Fortunately, in our experience, the tools that are most “ergonomic” for agents also end up being surprisingly intuitive to grasp as humans.
我们的目标，是扩大 agent 能有效解决问题的“作用面”——通过工具去尝试各种成功策略。好在根据我们的经验，对 agent 最好用的工具，对人类来说往往也出奇地直观。
How to write tools
怎么写工具
In this section, we describe how you can collaborate with agents both to write and to improve the tools you give them. Start by standing up a quick prototype of your tools and testing them locally. Next, run a comprehensive evaluation to measure subsequent changes. Working alongside agents, you can repeat the process of evaluating and improving your tools until your agents achieve strong performance on real-world tasks.
本节讲你如何与 agent 协作，来编写并改进你给它的工具。先做一个快速原型在本地测试；接着跑一套完整评测来衡量后续改动。与 agent 并肩工作，你可以反复“评测—改进”，直到 agent 在真实任务上表现足够强。
Building a prototype
做原型
It can be difficult to anticipate which tools agents will find ergonomic and which tools they won’t without getting hands-on yourself. Start by standing up a quick prototype of your tools. If you’re using Claude Code to write your tools (potentially in one-shot), it helps to give Claude documentation for any software libraries, APIs, or SDKs (including potentially the MCP SDK ) your tools will rely on. LLM-friendly documentation can commonly be found in flat llms.txt files on official documentation sites (here’s our API’s ).
不动手亲自试，很难预判哪些工具 agent 用着顺手、哪些不顺手。所以先做一版快速原型。如果你用 Claude Code 来写工具（可能一次就写出来），给它提供工具所依赖的软件库、API 或 SDK 的文档会很有帮助（包括 MCP SDK）。对 LLM 友好的文档通常以扁平的 llms.txt 形式放在官方文档站上。
我的批注★ 你这三周的核心困惑，Anthropic 用一句话回答了：『不动手亲自试，很难预判哪些工具 agent 用着顺手』。你从没试过，就判了自己死刑。

工具也可以直接传进 Anthropic API 调用里做程序化测试。
Test the tools yourself to identify any rough edges. Collect feedback from your users to build an intuition around the use-cases and prompts you expect your tools to enable.
自己试这些工具，找出粗糙的地方。收集用户反馈，建立你对“这些工具该支撑哪些用例和提示词”的直觉。
Running an evaluation
跑评测
Next, you need to measure how well Claude uses your tools by running an evaluation. Start by generating lots of evaluation tasks, grounded in real world uses. We recommend collaborating with an agent to help analyze your results and determine how to improve your tools. See this process end-to-end in our tool evaluation cookbook .
接下来要测量 Claude 用你这些工具用得多好，办法是跑评测。先围绕真实用途生成大量评测任务。我们建议与 agent 协作来分析结果、判断如何改进工具。完整流程见我们的 tool evaluation cookbook。
我的批注评测要围绕真实用途生成任务。你的真实用途是什么？『翻一页漫画让用户点头』——但你从没把它做成一条评测任务。

Generating evaluation tasks
生成评测任务
With your early prototype, Claude Code can quickly explore your tools and create dozens of prompt and response pairs. Prompts should be inspired by real-world uses and be based on realistic data sources and services (for example, internal knowledge bases and microservices). We recommend you avoid overly simplistic or superficial “sandbox” environments that don’t stress-test your tools with sufficient complexity. Strong evaluation tasks might require multiple tool calls—potentially dozens.
有了早期原型，Claude Code 能很快探索你的工具、造出几十组“提示词—回答”对。提示词应当来源于真实用途，基于真实的数据源和服务（例如内部知识库和微服务）。我们建议避免过于简单或表面的“沙盒”环境——那种环境不足以压测你的工具。强的评测任务可能需要多次工具调用，甚至几十次。
我的批注原文要求避免『过于简单或表面的沙盒环境』。你那些 probe_*.py 恰好就是原文说的弱任务。
Here are some examples of strong tasks:
强任务示例：
Schedule a meeting with Jane next week to discuss our latest Acme Corp project. Attach the notes from our last project planning meeting and reserve a conference room.
安排下周和 Jane 开会，讨论最新的 Acme Corp 项目。附上上次项目规划会的笔记，并订一间会议室。
Customer ID 9182 reported that they were charged three times for a single purchase attempt. Find all relevant log entries and determine if any other customers were affected by the same issue.
客户 ID 9182 报告说，一次购买尝试被扣了三次费。找出所有相关日志，并判断是否还有其他客户受同一问题影响。
Customer Sarah Chen just submitted a cancellation request. Prepare a retention offer. Determine: (1) why they're leaving, (2) what retention offer would be most compelling, and (3) any risk factors we should be aware of before making an offer.
客户 Sarah Chen 刚提交了取消申请。准备一份挽留方案，判断：(1) 他为什么走；(2) 最有吸引力的挽留条件是什么；(3) 报价前我们该注意哪些风险。

较弱的任务示例：

Each evaluation prompt should be paired with a verifiable response or outcome. Your verifier can be as simple as an exact string comparison between ground truth and sampled responses, or as advanced as enlisting Claude to judge the response. Avoid overly strict verifiers that reject correct responses due to spurious differences like formatting, punctuation, or valid alternative phrasings.
每条评测提示词都该配一个可验证的回答或结果。验证器可以简单到字符串精确比对，也可以高级到请 Claude 来当裁判。但要避免过于严格的验证器——不要因为它格式化、标点或另一种同样正确的说法就把对的判成错的。
我的批注验证器不要太严——不要因为它格式化、标点不同就把对的判成错的。你的 pytest 有几条正好犯这个毛病（EOL 检查、module-map 新鲜度）。
For each prompt-response pair, you can optionally also specify the tools you expect an agent to call in solving the task, to measure whether or not agents are successful in grasping each tool’s purpose during evaluation. However, because there might be multiple valid paths to solving tasks correctly, try to avoid overspecifying or overfitting to strategies.
对每一组提示词—回答，你还可以（可选地）写明你期望 agent 调用哪些工具，用来衡量 agent 有没有抓住每个工具的用途。但由于解决任务可能有多种正确路径，要尽量避免把策略规定得过死、过拟合。
Running the evaluation
跑评测
We recommend running your evaluation programmatically with direct LLM API calls. Use simple agentic loops ( while -loops wrapping alternating LLM API and tool calls): one loop for each evaluation task. Each evaluation agent should be given a single task prompt and your tools.
我们建议用直接调 LLM API 的方式程序化地跑评测。用简单的 agent 循环（while 循环里交替进行 LLM API 调用和工具调用）：每个评测任务一个循环。每个评测 agent 拿到一个任务提示词和你的工具。
In your evaluation agents’ system prompts, we recommend instructing agents to output not just structured response blocks (for verification), but also reasoning and feedback blocks. Instructing agents to output these before tool call and response blocks may increase LLMs’ effective intelligence by triggering chain-of-thought (CoT) behaviors.
在评测 agent 的系统提示里，我们建议不只是要求输出结构化回答块（供验证），还要它输出推理块和反馈块。把这些块放在工具调用和回答块之前输出，可能通过触发思维链（CoT）行为来提升 LLM 的有效智能。
If you’re running your evaluation with Claude, you can turn on interleaved thinking for similar functionality “off-the-shelf”. This will help you probe why agents do or don’t call certain tools and highlight specific areas of improvement in tool descriptions and specs.
如果你用 Claude 跑评测，可以打开 interleaved thinking 来获得类似效果（开箱即用）。这有助于你探查 agent 为什么调用或不调用某些工具，并指出工具描述和规格里具体该改哪里。
As well as top-level accuracy, we recommend collecting other metrics like the total runtime of individual tool calls and tasks, the total number of tool calls, the total token consumption, and tool errors. Tracking tool calls can help reveal common workflows that agents pursue and offer some opportunities for tools to consolidate.
除了顶层准确率，我们还建议收集其他指标：单次工具调用的耗时、任务总耗时、工具调用总次数、token 总消耗、工具报错。跟踪工具调用能揭示 agent 常采用的典型工作流，也提供了“哪些工具该合并”的线索。
我的批注原文建议记录：工具调用次数、耗时、token、报错。你今晚干的就是这件事（我数了 81 场会话），只是你把它当成了审判而不是测量。

Analyzing results
分析结果
Agents are your helpful partners in spotting issues and providing feedback on everything from contradictory tool descriptions to inefficient tool implementations and confusing tool schemas. However, keep in mind that what agents omit in their feedback and responses can often be more important than what they include. LLMs don’t always say what they mean .
在发现问题、给出反馈这件事上，agent 是有用的伙伴——从前后矛盾的描述，到低效的实现，再到难懂的工具 schema，它都能提。但要记住：agent 反馈和回答里“没说的”，往往比“说了的”更重要。LLM 并不总是说它真正想说的。
Observe where your agents get stumped or confused. Read through your evaluation agents’ reasoning and feedback (or CoT) to identify rough edges. Review the raw transcripts (including tool calls and tool responses) to catch any behavior not explicitly described in the agent’s CoT. Read between the lines; remember that your evaluation agents don’t necessarily know the correct answers and strategies.
留意 agent 在哪里卡住或困惑。通读评测 agent 的推理和反馈（或 CoT）找出粗糙处。检查原始记录（含工具调用与工具返回），抓住任何没被 CoT 显式描述的行为。要读弦外之音；记住评测 agent 未必知道正确答案和策略。
Analyze your tool calling metrics. Lots of redundant tool calls might suggest some rightsizing of pagination or token limit parameters is warranted; lots of tool errors for invalid parameters might suggest tools could use clearer descriptions or better examples. When we launched Claude’s web search tool , we identified that Claude was needlessly appending 2025 to the tool’s query parameter, biasing search results and degrading performance (we steered Claude in the right direction by improving the tool description).
分析你的工具调用指标。大量冗余调用可能意味着分页或 token 上限该调整；大量“参数非法”的报错可能意味着工具描述该更清楚、或该给更好的例子。我们上线 Claude 的网页搜索工具时发现，Claude 会无谓地在查询参数后面追加“2025”，这引入了偏向、降低了表现（我们靠改进工具描述把它引向正轨）。
Collaborating with agents
与 agent 协作
You can even let agents analyze your results and improve your tools for you. Simply concatenate the transcripts from your evaluation agents and paste them into Claude Code. Claude is an expert at analyzing transcripts and refactoring lots of tools all at once—for example, to ensure tool implementations and descriptions remain self-consistent when new changes are made.
你甚至可以让 agent 自己分析结果、替你改进工具。只要把评测 agent 的记录拼起来，粘进 Claude Code 即可。Claude 是分析记录、批量重构大量工具的专家——比如在做出新改动时，确保工具的实现与描述保持一致。
In fact, most of the advice in this post came from repeatedly optimizing our internal tool implementations with Claude Code. Our evaluations were created on top of our internal workspace, mirroring the complexity of our internal workflows, including real projects, documents, and messages.
事实上，本文大部分建议，都来自我们反复用 Claude Code 优化内部工具实现的过程。我们的评测建立在内部工作区之上，复刻了内部工作流的复杂度，包括真实项目、文档和消息。
We relied on held-out test sets to ensure we did not overfit to our “training” evaluations. These test sets revealed that we could extract additional performance improvements even beyond what we achieved with "expert" tool implementations—whether those tools were manually written by our researchers or generated by Claude itself.
我们依赖留出测试集来确保没有对“训练用”评测过拟合。这些测试集显示：即便与“专家级”工具实现相比，我们仍能榨出额外的表现提升——无论那些工具是研究员手写的，还是 Claude 自己生成的。

下一节，我们分享从这一过程中学到的东西。
Principles for writing effective tools
写出有效工具的原则
In this section, we distill our learnings into a few guiding principles for writing effective tools.
本节把我们学到的东西提炼成几条指导原则。
Choosing the right tools for agents
为 agent 选对工具
More tools don’t always lead to better outcomes. A common error we’ve observed is tools that merely wrap existing software functionality or API endpoints—whether or not the tools are appropriate for agents. This is because agents have distinct “affordances” to traditional software—that is, they have different ways of perceiving the potential actions they can take with those tools
工具更多并不总是带来更好结果。我们观察到的一个常见错误，是工具只是把已有的软件功能或 API 端点包了一层——不管这个工具是否适合 agent。原因在于，agent 与传统软件有着不同的“可供性”，也就是它们感知“自己能做哪些动作”的方式不同。
LLM agents have limited "context" (that is, there are limits to how much information they can process at once), whereas computer memory is cheap and abundant. Consider the task of searching for a contact in an address book. Traditional software programs can efficiently store and process a list of contacts one at a time, checking each one before moving on.
LLM agent 的“上下文”是有限的（一次能处理的信息量有上限），而计算机内存既便宜又充裕。想想在通讯录里找一个联系人：传统程序可以高效地逐个存储和处理联系人列表，一个一个查过去。
However, if an LLM agent uses a tool that returns ALL contacts and then has to read through each one token-by-token, it's wasting its limited context space on irrelevant information (imagine searching for a contact in your address book by reading each page from top-to-bottom—that is, via brute-force search). The better and more natural approach (for agents and humans alike) is to skip to the relevant page first (perhaps finding it alphabetically).
但如果 LLM agent 用了一个返回“全部联系人”的工具，然后必须逐 token 读完每一个，那就是在把有限的上下文浪费在无关信息上（想象你在通讯录里找一个人，却是从第一页开始逐页读到尾——也就是暴力搜索）。更好也更自然的做法（对 agent 和对人一样），是先跳到相关的那一页（也许是按字母顺序找到它）。
我的批注★ 这是全文最重要的一段：LLM 的上下文有限，而『返回全部再让它读』是暴力搜索。原文主张 search_contacts 而不是 list_contacts。你的 find_code.py 是对的方向，只是没挂到调用面上。
We recommend building a few thoughtful tools targeting specific high-impact workflows, which match your evaluation tasks and scaling up from there. In the address book case, you might choose to implement a search_contacts or message_contact tool instead of a list_contacts tool.
我们建议围绕特定的高价值工作流，精心构建少量工具，让它们与你的评测任务对应，再逐步扩展。在通讯录这个例子里，你可以选择实现 search_contacts 或 message_contact，而不是 list_contacts。
Tools can consolidate functionality, handling potentially multiple discrete operations (or API calls) under the hood. For example, tools can enrich tool responses with related metadata or handle frequently chained, multi-step tasks in a single tool call.
工具可以合并功能，在底层处理多个离散操作（或 API 调用）。例如，工具可以在返回内容里附上相关元数据，或者把经常需要连续多步完成的任务，合并成一次工具调用。
我的批注『我们建议围绕高价值工作流构建少量工具』——不是多多益善。这跟你自己定的『机制准入条件』是同一个道理。
Here are some examples:
示例如下：
Instead of implementing a list_users , list_events , and create_event tools, consider implementing a schedule_event tool which finds availability and schedules an event.
不要分别实现 list_users、list_events 和 create_event，而应考虑实现 schedule_event——它自己会查可用时段并安排事件。
Instead of implementing a read_logs tool, consider implementing a search_logs tool which only returns relevant log lines and some surrounding context.
不要实现 read_logs，而应考虑实现 search_logs——只返回相关日志行及其周边上下文。
Instead of implementing get_customer_by_id , list_transactions , and list_notes tools, implement a get_customer_context tool which compiles all of a customer’s recent & relevant information all at once.
不要实现 get_customer_by_id、list_transactions 和 list_notes，而要实现 get_customer_context——一次性汇总某客户近期且相关的全部信息。
Make sure each tool you build has a clear, distinct purpose. Tools should enable agents to subdivide and solve tasks in much the same way that a human would, given access to the same underlying resources, and simultaneously reduce the context that would have otherwise been consumed by intermediate outputs.
确保你做的每个工具都有清晰、独特的用途。工具应当让 agent 能像人拿到同样底层资源时那样，把任务拆开、逐个解决，同时减少本来会消耗在中间产物上的上下文。
Too many tools or overlapping tools can also distract agents from pursuing efficient strategies. Careful, selective planning of the tools you build (or don’t build) can really pay off.
工具太多、或功能重叠，也会分散 agent 的注意力，让它偏离高效策略。对“做哪些工具、不做哪些工具”做审慎而有取舍的规划，回报确实很大。
Namespacing your tools

Your AI agents will potentially gain access to dozens of MCP servers and hundreds of different tools–including those by other developers. When tools overlap in function or have a vague purpose, agents can get confused about which ones to use.
你的 AI agent 可能会接触到几十个 MCP server、几百个不同的工具——包括别人开发的。当工具功能重叠或用途含糊时，agent 会搞不清该用哪个。
Namespacing (grouping related tools under common prefixes) can help delineate boundaries between lots of tools; MCP clients sometimes do this by default. For example, namespacing tools by service (e.g., asana_search , jira_search ) and by resource (e.g., asana_projects_search , asana_users_search ), can help agents select the right tools at the right time.
命名空间（把相关工具归到共同前缀下）有助于在大量工具之间划清边界；MCP 客户端有时会默认这么做。例如按服务命名（如 asana_search、jira_search）或按资源命名（如 asana_projects_search、asana_users_search），能帮 agent 在正确的时候选到正确的工具。

我们发现，选择“前缀式”还是“后缀式”命名空间，对工具使用评测有不小的影响。影响因 LLM 而异，我们鼓励你按自己的评测来选择命名方案。
Agents might call the wrong tools, call the right tools with the wrong parameters, call too few tools, or process tool responses incorrectly. By selectively implementing tools whose names reflect natural subdivisions of tasks, you simultaneously reduce the number of tools and tool descriptions loaded into the agent’s context and offload agentic computation from the agent’s context back into the tool calls themselves. This reduces an agent’s overall risk of making mistakes.

Finally, we landed on creating a tool that Claude could call at any point, but it was particularly prompted to do so during plan mode. When the tool triggered we would show a modal to display the questions and block the agent's loop until the user answered.
最终，我们落到了“做一个 Claude 随时可调用的工具”上，同时特别提示它在计划模式下要调用。工具触发时，我们弹出一个模态框展示问题，并阻塞 agent 循环，直到用户回答。
This tool allowed us to prompt Claude for a structured output and it helped us ensure that Claude gave the user multiple options. It also gave users ways to compose this functionality, for example calling it in the Agent SDK or using referring to it in skills.
这个工具让我们能要求 Claude 给出结构化输出，也帮我们确保 Claude 给用户多个选项。它还给了用户组合这项能力的方式，比如在 Agent SDK 里调用它，或在 skill 里引用它。
Most importantly, Claude seemed to like calling this tool and we found its outputs worked well. After all, even the best designed tool doesn’t work if Claude doesn’t understand how to call it.
最重要的是，Claude 似乎很喜欢调用这个工具，而且我们发现它的输出效果很好。毕竟，即便设计得再好，如果 Claude 不知道怎么调用，这个工具也白搭。
我的批注原文原话：『即便设计得再好，如果 Claude 不知道怎么调用，这个工具也白搭。』——这句就是你 find_code.py 的墓志铭。
Is this the final form of elicitation in Claude Code? We doubt it. As Claude gets more capable, the tools that serve it have to evolve too. The next section shows a case where a tool that once helped started getting in the way.
这是 Claude Code 里提问能力的最终形态吗？我们很怀疑。随着 Claude 变得更强，服务于它的工具也必须跟着演化。下一节会讲一个案例：曾经有帮助的工具，后来开始碍事了。
Updating with capabilities: tasks & todos
随能力演进：tasks 与 todos
When we first launched Claude Code, we realized that the model needed a todo list to keep it on track. Todos could be written at the start and checked off as the model did work. To do this we gave Claude the TodoWrite tool, which would write or update Todos and display them to the user.
Claude Code 刚发布时，我们意识到模型需要一个待办清单来保持正轨。Todo 可以在开头写好，模型做一件事就勾掉一件。为此我们给了 Claude 一个 TodoWrite 工具，用来写入或更新 Todo 并展示给用户。
But even then, we often saw Claude forgetting what it had to do. To adapt, we inserted system reminders every 5 turns that reminded Claude of its goal.
但即便那时，我们也常看到 Claude 忘记自己该做什么。于是我们每 5 轮插入一次系统提醒，提醒它目标是什么。
As models improved, they found To-do lists limiting. Being sent reminders of the todo list made Claude think that it had to stick to the list instead of modifying it when it realized it needed to change course. We also saw Opus 4.5 also get much better at using subagents, but how could subagents coordinate on a shared todo list?
随着模型变强，它们觉得待办清单成了限制。被反复提醒清单，会让 Claude 以为必须死守清单，而不是在发现该改方向时去修改它。我们还看到 Opus 4.5 在子 agent 使用上强了很多，但子 agent 怎么在一个共享的待办清单上协作？
Seeing this, we replaced the TodoWrite feature with the Task tool . Whereas todos are focused on keeping the model on track, tasks help agents communicate with each other. Tasks could include dependencies, share updates across subagents and the model could alter and delete them.
看到这些，我们把 TodoWrite 功能换成了 Task 工具。todo 关注的是让模型保持正轨，而 task 帮助 agent 之间互相沟通。Task 可以带依赖、在子 agent 间共享更新，模型也可以修改和删除它们。
As model capabilities increase, the tools that your models once needed might now be constraining them. It’s important to constantly revisit previous assumptions on what tools are needed. This is also why it's useful to stick to a small set of models to support that have a fairly similar capabilities profile.
随着模型能力提升，模型曾经需要的工具，现在可能反而在束缚它们。持续重新审视“到底需要哪些工具”这个假设很重要。这也是为什么坚持只支持一小批能力档位相近的模型是有好处的。
我的批注★ 模型变强之后，原本有用的工具反而成了限制。原文的结论是：**要持续重新审视『到底需要哪些工具』**。你的删除行为，方向是对的。
Designing a search interface
设计搜索界面
The most consequential tools we've built are the ones that let Claude find its own context.
我们做过的影响最深远的工具，是让 Claude 能自己找到上下文的那些。
When Claude Code was first released internally, we used RAG: a vector database would pre-index the codebase, and the harness would retrieve relevant snippets and hand them to Claude before each response.. While RAG was powerful and fast, it required indexing and setup and could be fragile across a host of different environments. Most importantly, Claude was given this context instead of finding the context itself.
Claude Code 最初在内部发布时，我们用的是 RAG：向量数据库预先索引代码库，harness 在每次回答前检索相关片段交给 Claude。虽然 RAG 强大又快，但它需要索引和配置，而且在各种不同环境里容易出问题。最重要的是——这是把上下文“给”了 Claude，而不是让 Claude 自己去找。
But if Claude could search on the web, why couldn’t it also search your codebase? By giving Claude a Grep tool, we could let it search for files and build context itself.
但如果 Claude 能在网上搜索，为什么不能搜你的代码库？给它一个 Grep 工具，我们就能让它自己搜文件、自己构建上下文。
我的批注⭐⭐ 这一段是全文最反直觉的地方：**他们主动废掉了 RAG**，因为 RAG 是『把上下文给 Claude』，而不是『让 Claude 自己找』。
As Claude gets smarter, it becomes increasingly good at building its context when given the right tools.
随着 Claude 变聪明，只要给了合适的工具，它构建自己上下文的能力就越来越强。
我的批注★ 他们给 Claude 一个 Grep 工具，让它自己搜。**注意：他们给的是通用搜索工具，不是几十个专用工具。** 而你的项目里，grep 是原生工具、find_code 是命令行脚本——你的问题不是工具不对，是它没挂在手边。
When we introduced Agent Skills , we formalized the idea of progressive disclosure, which allows agents to incrementally discover relevant context through exploration.
当我们推出 Agent Skills 时，我们把“渐进式披露”这个概念正式化了：让 agent 通过探索，逐步发现相关上下文。
Claude could now read skill files and those files could then reference other files that the model could read recursively. In fact, a common use of skills is to add more search capabilities to Claude like giving it instructions on how to use an API or query a database.
Claude 现在能读技能文件，而那些文件又能引用其他文件供模型递归读取。事实上，技能的一个常见用法，就是给 Claude 增加更多搜索能力，比如教它怎么用一个 API、怎么查一个数据库。
Over the course of a year, Claude went from not really being able to build its own context to being able to do nested search across several layers of files to find the exact context it needed.
一年之间，Claude 从几乎无法自建上下文，进化到能跨多层文件做嵌套搜索，找到它需要的精确上下文。
Progressive disclosure is now a common technique we use to add new functionality without adding a tool. In the next section, we explain why.
渐进式披露现在是我们常用的技巧：在不增加新工具的前提下添加新功能。下一节解释为什么。
Progressive disclosure: the Claude Code Guide agent
渐进式披露：Claude Code Guide agent
Claude Code currently has ~20 tools, and our team frequently revisits if we need all of them for Claude to be most effective. The bar to add a new tool is high, because this gives the model one more option to think about.
Claude Code 目前大约有 20 个工具，我们团队经常重新审视：是不是全都需要，才能让 Claude 最有效。增加一个新工具的门槛很高，因为那等于多给模型一个要考虑的选项。
我的批注★ 原文承认：Claude Code 只有约 20 个工具，而且『增加一个新工具的门槛很高，因为那等于多给模型一个要考虑的选项』。这是 Anthropic 的官方立场，和你的『机制准入条件』完全一致。
For example, we noticed that Claude did not know enough about how to use Claude Code. If you asked it how to add a MCP or what a slash command did, it would not be able to reply.
举个例子，我们注意到 Claude 对“怎么用 Claude Code”了解不够。如果你问它怎么添加一个 MCP、或者某个斜杠命令是干什么的，它答不出来。
We could have put all of this information in the system prompt, but given that users rarely asked about this, it would have added context rot and interfered with Claude Code’s main job: writing code.
我们本可以把这些信息全塞进系统提示，但考虑到用户很少问这些，那会引入上下文腐化，并干扰 Claude Code 的主职：写代码。
Instead, we tried progressive disclosure: we gave Claude a link to its docs that it could load and search when needed. This worked, but Claude would pull large chunks of documentation into context to find an answer the user could have gotten in one sentence.
于是我们试了渐进式披露：给 Claude 一个它可以在需要时加载和搜索的文档链接。这办法管用，但 Claude 会把大段文档拉进上下文，只为回答一句本可以一句话回答的问题。
So we built the Claude Code Guide — a subagent Claude calls whenever a user asks about Claude Code itself. The subagent does the doc-searching in its own context, follows detailed instructions on how to search and what to extract, and hands back only the answer. The main agent's context stays clean.
于是我们做了 Claude Code Guide——一个子 agent，每当用户问起 Claude Code 自身时就被调用。这个子 agent 在自己的上下文里做文档搜索，遵循详细的搜索与提取指令，只把答案交回来。主 agent 的上下文保持干净。
While this isn’t a perfect solution (Claude can still get confused when you ask it about how to set itself up), we were able to add things to Claude's action space without adding a new tool.
虽然这并非完美方案（当你问它怎么配置自己时，Claude 仍可能糊涂），但我们做到了在不增加新工具的情况下，给 Claude 的行动空间添加了内容。
Seeing like an agent is an art, not a science
像 agent 一样看问题，是艺术，不是科学
Designing the tools for your models is as much an art as it is a science. It depends heavily on the model you're using, the goal of the agent and the environment it’s operating in.
为你的模型设计工具，既是科学，也是艺术。它在很大程度上取决于你用的模型、agent 的目标，以及它所处的环境。
Our best advice? Experiment often, read your outputs, try new things. And most importantly, try to see like an agent.
我们最好的建议？多做实验，读它的输出，去理解它。
我的批注★★ 这篇的结尾：『像 agent 一样看问题，是艺术，不是科学』。你自己定的标准是科学级别的保证——**连写这篇文章的团队都不承认这个标准存在**。

What is a verification loop?
什么是验证循环？
A verification loop is a repeating cycle where an AI agent checks its own work — running tests, linters, or custom checks — and fixes what fails before moving on. In Claude Code, verification loops can be packaged as skills, so every session applies the same checks automatically instead of relying on a human to remember them.
验证循环是一个重复的周期：AI agent 检查自己的工作——跑测试、linter 或自定义检查——并在继续之前修好失败的部分。在 Claude Code 里，验证循环可以打包成技能，这样每个会话都会自动套用同样的检查，而不是依赖人来记住。

在设计自定义验证循环之前，先了解 Claude 对若干验证循环的内置支持会很有帮助。常见的功能与做法包括：

Toolchain : Claude aims to catch and act on error codes and warnings from any tool you provide such as a linter. A good practice is to list your exact build and test commands in CLAUDE.md so Claude doesn't have to infer them.
工具链：Claude 会捕捉并响应你提供的任何工具发出的错误码和警告，比如 linter。一个好做法是在 CLAUDE.md 里列出你确切的构建与测试命令，这样 Claude 不用去猜。

Writing verification loops
写验证循环
When you have an existing project and you find yourself making the same small corrections every time Claude implements a new feature for you, it’s time to turn those steps into your own custom verification loop. The first step is to write down everything that you find yourself doing every time
当你已有一个项目，并且发现每次 Claude 为你实现新功能时，你都要做同样的一些小修正，这时候就该把这些步骤变成你自己的自定义验证循环。第一步是写下你每次都在做的所有事情。
我的批注★ 原文给的定义：验证循环 = 『AI agent 检查自己的工作并尝试修复』。这就是你的 state.py finish。**你已经做到了这篇文章讲的核心。**
The same goes if you're starting a new project and need to figure out how the project should behave. Write the best-practices version in plain English, the way you'd hand it to a new teammate on day one.
如果你是新建项目、需要弄清项目应当如何表现，道理也一样。用人话写出“最佳实践版”，就像你第一天交给一个新同事那样。
If you're struggling to articulate the verification check itself, ask Claude for best practices first and edit from there. Your version probably differs on a few specific points, and those differences are exactly what you want to capture.
如果你连这条验证检查本身都难以说清，就先让 Claude 给出最佳实践，再在此基础上改。你的版本大概会在几个具体点上不同，而那些不同正是你想捕捉的东西。
Pro tip : The check doesn't have to be qualitative to belong here. "Reject any migration that drops a column without a backfill step" is a deterministic rule no generic linter will catch but a project-specific one will. Anything you keep having to enforce by hand as a manual check qualifies for capture as a loop.
专业提示：检查不必是定性的才能放进来。“拒绝任何删除列却没有回填步骤的迁移”就是一条确定性规则——通用 linter 抓不到，项目专用的能抓到。任何你一直在手工强制的检查，都有资格被固化成循环。
我的批注★ 原文说：先写下你每次都在做的人工步骤。**这就是你缺的那一步**——你的判断每次都做了，但从没写下来过。
Make it a skill
做成技能
The most common way to encode repetitive steps into a verification loop is to write it as a skill, and the fastest way to create a skill is to install the skill-creator plugin and let Claude interview you:
把重复步骤编码成验证循环，最常见的方式是写成技能；而创建技能最快的方法，是装上 skill-creator 插件，让 Claude 来采访你。
Example:
你也可以手写技能：在项目的 .claude/skills/ 里丢一个 markdown 文件。最简单的验证技能就是几行 frontmatter 加一段正文。
/skill-creator Create a skill for verifying frontend changes end-to-end. Interview me about my workflow.
匹配检查与它的运行时机
You can also hand-write a skill by dropping a markdown file in .claude/skills/ inside your project. The simplest possible verification skill is a few lines of frontmatter plus a body:

# .claude/skills/verify-log-hygiene/SKILL.md --- name: verify-log-hygiene description: Check that error logs include the request ID and never include the request body. Use when the diff touches error handling or logging. allowed-tools: [Read, Edit, Grep] --- Read the error-handling paths in the current diff. For each log call on an error path, confirm it includes the request ID and does not pass the request body, headers, or any user-supplied payload. Report each violation with file:line, then fix it: add the request ID where it's missing and strip the payload from the log call.
独立式（Standalone）
The full schema and the philosophy behind it are in our complete guide to building skills.
你刻意地调用它，在产物已经存在之后。独立式技能对“不是每次都适用”的横切检查有价值：提交前的安全扫描、PR 前的无障碍审计、全仓库的许可证头校验。任何你想在很多工作流里随时可用、但不想每次代码改动都触发的东西。
我的批注★ 专业提示里给了一个判断标准：『任何你一直在手工强制的检查，都有资格被固化成循环』。也就是说，先有人工重复，后有循环。你现在还没有重复。
Match the check to where it runs
代价是：每次调用仍然是你要记得去做的一个回合。你已经“成长到超出独立式”的信号，是你每次改动之后都会去跑它。到那时，这个流程就挣到了一个永久的家：把它嵌入，或者链式串起来。
The next thing to determine will be how the verification loop kicks off: standalone, embedded, chained, or tied to PR.
嵌入式（Embedded）
Standalone
作为产出型技能的一部分自动触发。这项检查属于某个特定工作流，而该工作流现在会在你不要求的情况下就执行它。
You invoke it deliberately, after the artifact exists. A standalone skill earns its place for cross-cutting checks that don't apply every time: a pre-commit security scan, a pre-PR accessibility audit, license-header verification across a repo. Anything you want available across many workflows but don't want firing on every code change.
最简单的版本，就是在产出型技能的正文末尾追加一行。
The cost is that each invocation is still a turn you have to remember to take. The signal that you've outgrown standalone is when you're running it after every change. At that point, the procedure has earned a permanent home: embed it or chain it.
验证嵌入是否生效的办法是：在一个全新任务上调用该技能，确认新增的步骤作为输出的一部分被执行了。如果没有，说明该技能的描述或前面的指令没能把追加的检查带进来。
我的批注★ 注意这里的措辞：原文承认『不可靠』是常态，解决办法是**在新任务上再试一次**，不是『必须一次做对』。
Embedded
嵌入式只适用于你能编辑的技能：你自己写的，或者安装在项目层、SKILL.md 文件在你控制之下的。内置技能和插件管理的技能（升级时会被覆盖的那种）不能这么用；对它们，改用链式。
Fires automatically as part of the producing skill. The check belongs to one specific workflow, and the workflow now runs it without you asking.
跨多个工作流的检查不要用嵌入式；那些要用独立式，这样你能从任何上下文调用它们。
The simplest version is a one-line append to the producing skill's body:
链式（Chained）
