瓶颈定位（全部实测，非推测）

1. prompt eval（图像 prefill）占 95%+ 耗时

项数值说明
每张总耗时20-40s10 张基线 313.4s，均值 31.3s
其中 prompt eval29-36s / 208-229 tokens6-8 tok/s（BF16）；图像 token 是大头
输出生成（decode）<2sOCR 输出只有 2-20 tokens，可忽略

2. 视觉 token 数与输入尺寸无关（缩放图无效）

实测 88×78 小图与 25×224 竖长图都产生 ~208-229 个视觉 token——llama.cpp 按 mmproj 配置统一缩放图像。因此「把 crop 图改小」无法提速（已实测验证 max_side=224 缩放无收益）。

3. BF16 全精度是主拖累

主模型 892MB BF16（16BPW，未量化）。Q8_0 后 473MB，prompt eval 从 6-8 tok/s 提到 9-10 tok/s（+30%）。mmproj（视觉塔）840MB BF16 无法 Q8_0 量化（张量列 4304 非 32 倍数，属模型结构限制，保持 BF16）。

4. 隐藏正确性 bug：prompt cache 误命中

连续请求不同图像时，llama.cpp 按 token 序列匹配缓存——不同图产生相同 patch 网格时缓存误命中：0.1s 秒回上一张图的结果。实测 gt05 开缓存 0.1s 返回 'と'，关缓存 39s 返回 'しかし、'。此前部分评测结果可能被污染（如 preds_for_manga.json 中 gt00 输出与 GT 完全不符的多行文本）。

#方案预期风险/注意
1默认切 baberu-OCR（已有 ONNX 模型），For-Manga 作高精度/复杂场景备用101 张从 ~53min → ~2min先跑一次全量 101 张 CER 对比再定（本轮只测了 10 张对白）；长文本漏识别需回退策略（空输出→For-Manga）
2升级 llama.cpp（b10582 → 最新稳定版）VLM 多项性能优化（--fit 自动裁剪、flash attn 改进）CLAUDE.md 钉版本教训（≥b10582 才能跑 PaddleOCR-VL），升级后必须 smoke 验证
3评估官方推荐 OCR 模型（GLM-OCR / Deepseek-OCR / LFM2.5-VL-450M，Q8_0 现成）可能比 PaddleOCR-VL 快数倍日文竖排漫画场景需实测（通用 OCR 对漫画竖排系统性弱）
4请求层：图片 JPEG 化（PNG→JPEG q85）+ HTTP Session 复用传输/解码小幅提速收益小（local 传输开销占比低）
⚠️ 不建议：图像缩放提速（实测无效，token 数与尺寸无关）；CPU 多并发（L4 教训 workers=1，会崩）。
