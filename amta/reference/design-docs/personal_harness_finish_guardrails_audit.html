Personal Harness

本次讨论最终收敛为两个核心工程问题：Finish / Learning Loop 与 Guardrails + Audit。

核心原则：不要让 AI 只“记住错误”；让 AI 把错误编译成系统约束。

目标 01

每个任务结束后重新验收、检查 diff、运行验证、修复问题，并提炼真正值得长期保存的经验。

目标 02

通过编码中、pre-commit、pre-push 三层机械防线减少重复报错，再用周期性 audit 清理 Harness entropy。

  1. 重新读取任务与验收标准。
  2. 检查 git diff、无关修改、debug 残留、架构漂移。
  3. 运行 formatter、lint、typecheck、tests、build 等项目已有检查。
  4. 失败则诊断 → 修复 → 重跑。
  5. 判断是否产生可复用 lesson。
  6. 只在必要时更新 progress / lessons / rules / decisions。
  7. 判断稳定规则是否可以升级为 test/lint/hook。
  8. 最终验证后才宣布完成。

4. Finish 与 Hook 的边界

Finish = Brain

判断任务是否完成、为什么出错、是否形成 lesson、是否升级 rule、是否可以机械化。

Hook = Enforcement

自动运行 lint、阻止危险操作、执行固定检查、在生命周期节点触发确定性流程。

不要让 Hook 无脑把每次任务都写入所有 memory 文件。经验归纳属于 Agent 的 Finish 阶段。

5. 三层 Guardrails

阶段目标适合检查
During Coding秒级发现廉价错误format、syntax、轻量 lint、基础 schema check
pre-commit阻止明显不合格代码进入 Gitformat、lint、typecheck、相关 unit tests、架构检查
pre-push离开本地前强验证full tests、integration、build、E2E smoke、architecture tests
不要每次编辑都跑完整测试：开发中快，commit 中等，push 更严格。

6. Guardrail 应保护项目不变量

source files must not be overwritten
generated output must be separated from source
module A must not import module C directly
every pipeline stage must preserve page_id
external API responses must be schema-validated
情况落点
能机械判断test / lint / structural test / hook
不能机械判断，但 Agent 必须知道CLAUDE.md / scoped rules
属于程序性工作流skill / /finish

7. /audit：Harness Garbage Collection

Memory

CLAUDE.md 是否膨胀？规则重复/冲突？lesson 过时？哪些 lesson 可自动化？

Architecture

模块边界是否漂移？新增依赖是否合理？是否出现重复实现？

Verification

重复错误是否缺少 regression test？重要 invariant 是否仍只存在于 prose？

Hygiene

dead files、temporary artifacts、stale docs、错误提交的 generated files。

Audit 的目标不是生成巨型报告，而是找到下一批可以“编译”为约束的东西。

9. 面向 DeepSeek 的实施任务

INSPECT → PLAN → SHOW PROPOSED CHANGES → IMPLEMENT → VERIFY

先审计 CLAUDE.md/AGENTS.md、memory、scripts、项目配置、tests、lint、typecheck、hooks、Git、architecture、agent commands/skills。

然后报告：当前 Harness、缺失项、冗余项、Finish 生命周期、During Coding / pre-commit / pre-push 检查、Audit 范围与频率、lesson→rule→test/hook 晋升机制，以及 Phase 1/2/3 实施计划。

不要直接重写现有 Harness；已有有效机制优先保留并改进。

10. 与 OpenAI / Anthropic 官方思路的对应

本方案对应官方思想
Repository 作为知识载体OpenAI 强调 repository 是 agent 工作环境，并把意图、工具和反馈回路工程化。
失败 → capability → constraintOpenAI：失败时寻找缺失能力，并让它对 Agent 可见、可执行。
CLAUDE.md / rulesAnthropic：项目事实与稳定规则进入 CLAUDE.md / rules。
Finish / skillAnthropic：程序性工作流适合 skill，而不是把长流程塞进 CLAUDE.md。
HooksAnthropic：确定性生命周期自动化适合 hooks。
GuardrailsAnthropic：真正必须遵守的规则应使用确定性 guardrail，而不是只依赖提示。
Audit与 OpenAI 的持续质量治理、架构约束和减少系统熵增的思路一致。
