三、关键发现

🔍 发现 1：新实现反而更短（-7.4%）

region_id 从 page_19_u00（11字符）简化为 u00（3字符），11条就省了 88 字符，完全覆盖了 category 标注和页码分隔的额外开销。信息更丰富但 token 更少。

🔍 发现 2：category 全是 dialogue_bubble 的根因在 detection 阶段

用户质疑"这9页不可能全都是 dialogue bubble"。调查发现：category 生成链路是 Detection → OCR（optional passthrough）→ Canon → get_context。根因在 detection 阶段的 comic-text-bubble-detector 只检测对话气泡，不检测 SFX。get_context 只是忠实透传，不应该用硬编码兜底。

🔍 发现 3：避免硬编码业务逻辑，用数据自带字段过滤

术语筛选不用魔法数字（">20字跳过"），而是用数据自带的 status=confirmed 过滤。资源控制参数（MAX_REGIONS=15 / MAX_RELATIONSHIPS=3 / MAX_TERMS=5）是合理的，放在文件顶部做常量；业务判断阈值（长度、比例）不是。

🔍 发现 4：get_context 是透明数据传递层

get_context 只负责"读数据 → 匹配 → 格式化 → 输出"，不包含"智能判断"业务逻辑。判断数据质量是上游 detection/OCR 的事。这符合"最小披露"和"职责单一"原则。

四、实现内容

新增 5 个辅助函数

函数职责
_build_semantic_context主入口，组装结构化上下文
_read_page_blocks_from_artifacts读单页 canon+translation，按 region_id 匹配
_read_fallback_context回退到旧的汇总 translation.json / prev_pages
_format_relationships格式化角色关系（最多3条，confirmed优先）
_format_relevant_terms筛选前页相关术语（最多5条，只显示confirmed）

常量（资源控制参数，非硬编码业务逻辑）

  • CATEGORY_LABELS：dialogue_bubble→对话，overlay_text→覆盖文字，sfx→拟声
  • MAX_REGIONS_PER_PAGE = 15
  • MAX_RELATIONSHIPS = 3
  • MAX_TERMS = 5

五、与 manga-image-translator 对比

维度manga-image-translator本项目（新实现）
注入方式预取式（set_prev_context 自动注入）按需式（get_context 工具，LLM 决定何时调）
category 标注无（前页上下文是纯文本）有（dialogue_bubble/overlay_text/sfx）
角色关系独立 RelationshipMemory（方向性关系+冲突检测+置信度）work_state.relationships（简单结构，无冲突检测）
风格指南独立 YAML 文件work_state.terms（分散）
条数限制context_pages: 0..20MAX_REGIONS=15, MAX_RELATIONSHIPS=3, MAX_TERMS=5

关键差异：manga 是预取式（每次翻译都注入），本项目是按需式（LLM 主动调）。按需式更省 token，但依赖 LLM 主动调用。本项目的 category 标注比 manga 更细（manga 的前页上下文是纯文本，没有 category 标注）。
