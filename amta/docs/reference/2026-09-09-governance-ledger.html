② fastcheck 是不是包含 static / linter / typecheck / test 这 4 层？命令入口、hook、它仨啥关系？
你复读的 4 层全中，而且实际是 8 道工序（读 fastcheck.py 源码逐行确认）：
1 compile语法门(你说的 static)
2 rufflinter
3 pyrighttypecheck
4 pytest=npm test
5 depguard依赖守卫
6 mem-lint记忆活性
7 mem-gc记忆清理
8 mem-inject重写注入包
三个概念用「工厂」比喻一次分清：
  • fastcheck = 一台质检流水线机器（里面 8 道工序，本身是被动的，谁按开关它都跑同一套）。
  • 命令入口（npm run fastcheck / run.ps1）= 你手按的开关/快捷键，主动敲才跑。
  • pre-push hook = 装在「git push 按钮」底下的自动感应开关，你一按 push，它自动替你启动质检机，不合格把货弹回。它不是质检本身，是「自动触发质检」的机关。
所以「这个是护栏吗」——hook 是护栏（自动、代码强制），fastcheck 是护栏调用的检查内容，npm script 是手动版同款。殊途同归到同一台机器，保证你手动/自动跑的是同一套标准。

④ skill 是不是每次会话启动都烧 token？正文不是按需读吗，为啥还要砍？
skill 分两层加载，你只看到了第二层：
  • 目录层（每轮都在烧）：每个 skill 的 name + 一句话 description 会进 AI 的工具目录，AI 靠它判断「该不该用这个 skill」。实测 36 个项目 skill 的目录合计 8569 字节 ≈ 2678 token，哪怕一个正文都不读，这笔钱每轮固定花，且 36 选 1 本身就是选择负担（选项越多越难选对）。
  • 正文层（按需，不固定烧）：SKILL.md 全文只有 AI 判定需要时才 Read——你这点理解是对的。
关于「要不要手动 / 调用」：AI 可以全自动——看到 description 匹配就自己去 Read，不需要你 / 键入；你 /xxx 只是「强制手动挡」。你观察到的「AI 不主动用」，是路由槽位不够硬（老问题），不是 skill 天生必须手动。
所以砍 skill 的硬理由成立：砍的是每轮 2.7k token 的目录税 + 选择噪音。确定无用的现在就能砍；拿不准的等观测命中数据。

⑥ amta-memory 自造轮子能滚吗？MCP 是不是只有 Claude Code 能用，DSH 行不行（context7/supabase/vercel 都是在 CC 终端授权的）？
MCP 是开放标准（Model Context Protocol），不是 Claude Code 专属——Cursor / Codex / DSH 都能接，一个 MCP server 可同时被多个客户端连。
DSH 的接法（已查证）：DSH 内核不自带 MCP，但官方有 @deepseek-ai/dsh-mcp-client 插件，装上后在 cordis.patch.yml 给每个 server 挂实例，工具以 mcp__服务器__工具 注册，命名和 Claude Code 一致，.mcp.json 字段可「直接搬」。
  • context7：标准 MCP server → 搬配置即可。
  • supabase / vercel：在 CC 里是官方插件形态，迁 DSH 要走 MCP/社区桥，不是自动继承。
amta-memory（mcp_memory.py）去留：它只是自研记忆 M1 的「MCP 拉取入口」之一（M1 另有 CLI 和注入两个入口）。你说没实战——静态看确实主要靠 CLI+注入。但别急删：① 有没有会话真调过要靠观测；② 一旦主力迁 DSH，MCP 反而是记忆最自然的接入方式，删了可能又要重建。先标 待观测。
