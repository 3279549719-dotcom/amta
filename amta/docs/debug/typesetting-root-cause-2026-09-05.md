### 直接原因
`page_14_translation.json` 生成时间 `2026-09-05T11:35:44`，**早于**修复 commit `312cd64`。后续只重跑了 typeset 阶段（`18:43:39`），翻译数据是旧的、已错位的。

### 根本原因：数组契约的盲区
ADR-031 声称"数组契约防止 LLM 拆条挤占 region_id"，但 `parse_translation_array()` 只校验**数量相等**：

```python
# translate.py:81-97
def parse_translation_array(raw, expected_count):
    ...
    if len(data) != expected_count:
        return None   # 数量不符才失败
    return [str(v).strip() for v in data]
```

LLM 的实际行为：把输入第 2 条（r01）拆成 2 条译文、第 3 条（r02）拆成 2 条译文，然后**丢弃最后 2 条输入**（r10/r11）。输出总数仍然 = 12 = 输入数，数组契约校验通过。

`mechanical_guardrails()` 也只查 region_id 存在性和非空，不查语义对应：

```python
# guardrails.py:15-28
def mechanical_guardrails(canon, translation):
    for r in canon:
        if rid not in translation: problems.append(...)
        elif not translation[rid].strip(): problems.append(...)
    # 不检查译文与原文的语义/长度对应关系
```

### 修复方向
1. **立即**：用当前代码重跑 p11–p15 翻译阶段，确认数组契约+二分拆分能正确绑定
2. **增强护栏**：增加译文-原文字符长度比异常检测（如原文 30 字译文只有 4 字 → 可疑）
3. **增强护栏**：增加术语命中校验（r04 原文含"サグ姉"，译文必须含"探女姐"或"萨古姐"）

## 三、问题①：横竖方向不一致（P1，严重）

### 现象
- **p11 r04**：原文「そんなことより研究研究」是**横排**大字（bbox 宽 380×高 222），译文被排成**竖排 5 列**
- **p13 r02**：原文「お、落ち着け…別に八意様が…」是**竖排**（bbox 宽 166×高 691，高宽比 4.16），译文被排成**横排 9 行每行 2 字**（"伪竖排"）
- **p11 全部 7 个区域**：无一例外全选了 vertical，包括横长框

### 根源：fit_font_size 纯字号最大化，零方向约束

```python
# typeset_engine.py:94-106
def fit_font_size(text, font_path, bbox, ...):
    h_size, h_lines = _max_size_for_direction(..., "horizontal")
    v_size, v_lines = _max_size_for_direction(..., "vertical")
    if v_size >= h_size:        # ← 纯比字号，平局偏向竖排
        return v_size, "vertical", v_lines
    return h_size, "horizontal", h_lines
```

**设计缺陷**：ADR-031 删除了 `decide_direction`，改为"同时算横竖排最大字号选最优"。这在字号维度是第一性原理，但**完全丢失了"尊重原文阅读方向"的约束**。

### 具体机制分析

**案例 A：p11 r04（横长框被选竖排）**
- bbox 380×222，文本 11 字，MAX_SIZE=52
- 横排 52px：每行约 5 字 → 3 行，行高 62.4×3=187 < 189 ✓
- 竖排 52px：每列约 3 字 → 4–5 列，列宽 59.8×5=299 < 323 ✓
- **两者都触达 MAX_SIZE=52 天花板**，`v_size >= h_size` 平局 → 选竖排
- 短文本普遍触顶，方向选择近乎随机（平局偏竖排）

**案例 B：p13 r02（窄长框被选横排）**
- bbox 166×691，文本 19 字
- 竖排 52px：每列 9 字 → 19 字需 3 列，3×59.8=179 > 141 ✗ → 竖排最大 48px
- 横排 52px：每行 2 字 → 9–10 行，10×62.4=624 < 587？需精确验算
- 横排字号 > 竖排字号 → 选横排，导致每行 2 字的"伪竖排"

### 管线层面：方向信号全程缺失

```
detection (RT-DETR) → canon → translation → typeset
     ↓                    ↓          ↓           ↓
  只输出 bbox         无 direction  无 direction  fit_font_size
  bubble_type         字段          字段          纯算字号
  (text_bubble/       字段
   text_free)
```

- `detection.json`：只有 `bbox` + `bubble_type`，**无文字方向字段**
- `canon.json`：继承 detection，无 direction
- `koharu_blocks.py`：只有 `sort_by_reading_order`（阅读序排序），不检测单条文字方向
- RT-DETR 模型本身可能输出角度/方向信息，但未被提取到 schema 中

### 修复方向
1. **短期（零模型改动）**：从 bbox 长宽比推断方向——高宽比 > 1.5 推断竖排，宽高比 > 1.5 推断横排，接近方形时回退到字号选优。传入 `fit_font_size` 作为 `preferred_direction`，优先在该方向下最大化字号，仅当首选方向字号 < 次选方向 70% 时才切换
2. **中期**：从 OCR 结果（hayai）提取文字方向，或用 bbox 长宽比 + 文本长度联合判断
3. **长期**：RT-DETR 后处理增加方向分类头，或用轻量 CNN 判断裁剪区域内文字方向

## 四、问题②：竖排标点横置（P2，中等）

### 现象
- 竖排文本中的省略号「……」是**水平排列**的六个点，在竖排文字流中非常突兀
- p11 r01「非常相似。说不定……」竖排时，「……」横置
- p11 r03「连我自己都觉得真是异想天开啊……」同上

### 根源：渲染层逐字绘制，无竖排标点旋转

```python
# typeset_render.py:30-44
if direction == "vertical":
    for col_idx, col_text in enumerate(lines):
        for ch in col_text:
            draw.text((x, y), ch, font=font, ...)  # ← 每个字符原样绘制
            y += lh
```

- 「……」「——」「～」等宽型标点在竖排中应旋转 90°
- 当前代码对所有字符一视同仁，不做任何旋转
- 另外 `wrap_vertical()` 是简单切片，**无竖排避头尾**（标点不应出现在列首）

### 修复方向
1. 竖排渲染时，对 `……——～〜` 等字符执行 90° 旋转后绘制
2. 竖排折行增加避头尾规则（`NO_START_PUNCT` 不适用于列首）
3. 考虑使用支持竖排的字体（如 @font-face 竖排字体）或 PIL 的 `direction='ttb'`（如可用）
